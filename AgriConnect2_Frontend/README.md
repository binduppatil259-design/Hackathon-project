# AgriConnect 2.0 — Agricultural Marketplace Frontend

AgriConnect connects two core stakeholder groups through role-specific workspaces:

1. **Farmers** — manage produce listings, compare market information, discover buyer requirements, and explore aggregation options.
2. **Buyers** — prepare buying requirements, browse available produce, and organize enquiries and orders.


The frontend is built with HTML, CSS and vanilla JavaScript. The existing visual language is retained, with a new role selection and account access experience and separate navigation/workspaces for each stakeholder.

## Run locally

1. Extract the ZIP.
2. Open `index.html` in a modern browser, or serve the folder with a local static server for a more reliable development experience.
3. Select either Farmer or Buyer.
4. Choose Log in or Create account and complete the form.
5. Navigate the role-specific workspace.

**Important:** When API mode is disabled, the account screen opens a local workspace for interface evaluation; it does not authenticate an identity or create a secure account. Enable and test the backend authentication service before using real users or deploying publicly.

## Configuration

Edit `config.js`:

```js
window.AGRI_CONFIG = {
  USE_API: true,
  API_BASE_URL: 'http://localhost:8000',
  REQUEST_TIMEOUT_MS: 12000
};
```

Set `USE_API: true` only when the backend is running and the endpoint contracts below are implemented. Keep API keys and model credentials on the server; never put secrets in frontend JavaScript.

## Frontend/API contract to align with the backend

The current frontend expects or proposes these endpoints. They are integration contracts, not a claim that the backend already implements them. Agree on exact JSON schemas, status codes and authentication requirements with the backend developer.

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/auth/login` | Authenticate a user; response should include a user profile and role. |
| POST | `/api/auth/register` | Register a farmer, buyer or buyer. |
| GET | `/api/me` | Retrieve the authenticated user's profile. |
| GET | `/api/produce` | Retrieve authorized produce listings. |
| POST | `/api/produce` | Create a produce listing. |
| PATCH | `/api/produce/{id}` | Update an authorized listing. |
| DELETE | `/api/produce/{id}` | Archive or remove an authorized listing. |
| GET | `/api/buyer-demands` | Retrieve active buyer requirements. |
| POST | `/api/buyer-demands` | Create a buyer requirement. |
| POST | `/api/matches` | Return buyer matches and explanations for crop, quantity and market scale. |
| GET | `/api/market-prices?crop=...&area=...` | Return sourced market prices, units, market and observation time. |
| POST | `/api/aggregation/simulate` | Return a proposed compatible group and cost estimates. |
| POST | `/api/assistant/chat` | Return an answer generated by the configured server-side assistant service. |
| GET | `/api/orders` | Retrieve authorized order activity. |

Recommended additional endpoints include `POST /api/offers`, `PATCH /api/offers/{id}`, `POST /api/aggregation`, `GET /api/aggregation/{id}`, and `POST /api/aggregation/{id}/confirm`.

## Recommended response conventions

- Use consistent JSON responses and meaningful HTTP status codes.
- Validate all inputs on the server; browser validation is for usability only.
- Enforce role-based authorization on every protected endpoint. Never trust the role submitted by the browser as proof of permission.
- Market-price responses should identify the data source, market, unit, observation timestamp and freshness.
- Buyer-match responses should explain the match criteria and clearly separate confirmed offers from estimates.
- Aggregation simulation must not silently create or confirm an order.
- The AI assistant should only receive user-authorized context and must not invent prices, buyer availability or transaction status.
- Store passwords securely using an established password-hashing algorithm; use secure sessions or appropriately managed tokens, HTTPS, rate limits and audit logging in production.

## Role-specific workspaces

AgriConnect provides two distinct workspaces:

- **Farmer:** create and manage produce listings, set an asking price per kilogram, compare market prices, discover suitable buyers, and review aggregation options.
- **Buyer:** browse farmer listings, filter by crop/region/quantity, publish bulk buying requirements, and review order activity.

Both workspaces share marketplace data through backend APIs. When `USE_API` is disabled, authentication and submissions are local previews only; no real account is verified and data is not permanently stored. Configure the backend before using the app with real users.

### Additional API contracts

- `POST /api/produce` accepts `crop`, `quantity`, `quality`, `askingPrice`, `availableDate`, `location`, and `notes`.
- `GET /api/marketplace/produce` returns public available listings for buyer browsing (the backend should enforce role and visibility rules).
- `POST /api/buyer-demands` creates a buyer purchase requirement.
- `POST /api/offers` or an equivalent endpoint should record buyer enquiries against a listing. The current frontend should not represent an enquiry as a confirmed purchase until that API is implemented.

- `POST /api/offers` records a buyer enquiry for a listing.


## Order tracking frontend

Both Farmer and Buyer workspaces now include an **Order tracking / Order fulfilment** page. The interface displays order summaries, a lifecycle timeline (placed, confirmed, preparing, dispatched, in transit, out for delivery, delivered, receipt confirmed), expected delivery, participants, order value, latest reported location when supplied by the backend, and role-specific actions. Farmers can start preparation and record dispatch; buyers can confirm receipt after delivery.

### Order tracking API contract expected by the frontend

- `GET /api/orders` — return only orders the authenticated account is allowed to view. Response may be an array or `{ "orders": [...] }`. Each order should include `id`/`orderId`, `status`, `crop`, `quantity`, `farmerName`, `buyerName`, `deliveryDate` or `expectedDelivery`, and optional `events`/`trackingEvents`.
- `GET /api/orders/{id}/tracking` — return order details plus timestamped tracking events and optional latest location.
- `PATCH /api/orders/{id}/status` — accept permitted status transitions, such as `preparing` and `in_transit`, with authorization enforced server-side.
- `POST /api/orders/{id}/dispatch` — record dispatch and append a timestamped event.
- `POST /api/orders/{id}/confirm-receipt` — buyer-only receipt confirmation after delivery.

The frontend calls these routes when `USE_API` is enabled in `config.js`. The backend must implement the endpoints, authenticate the user, authorize access to each order, validate status transitions, and persist events. If API mode is disabled, the tracking screen shows an honest empty state rather than fabricated shipments.

**Live GPS note:** the UI only displays a location if the API returns one. Live map movement and ETA require a real driver GPS feed or logistics-provider integration; this frontend does not simulate a truck's location.
